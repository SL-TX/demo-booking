# Бронирование переговорных

API бронирования переговорных комнат в двух офисах — Москва (`Europe/Moscow`) и Новосибирск
(`Asia/Novosibirsk`). Laravel 13, PostgreSQL 17, Sanctum.

- Разбор исходной реализации и список дефектов — [`REVIEW.md`](REVIEW.md).
- Как выполнялась работа с ИИ и что проверялось вручную — [`AI_NOTES.md`](AI_NOTES.md).
- Техническая спецификация и план реализации — [`docs/superpowers/`](docs/superpowers/).

## Запуск

Нужны Docker и Docker Compose.

```sh
docker compose up -d --wait
docker compose exec app php artisan migrate:fresh --seed
```

Первый запуск занимает несколько минут: контейнер устанавливает зависимости. API доступно по
адресу `http://localhost:8000/api`.

## Тесты

```sh
docker compose exec app php artisan test
```

Тесты идут на PostgreSQL в отдельной базе `testing`.

## Правила брони

- Брони одной комнаты **не пересекаются**. Встречи «впритык» разрешены: 10:00–11:00 и 11:00–12:00 —
  это не пересечение.
- Длительность — **от 15 минут до 4 часов**, шаг — **15 минут** (10:00, 10:15, …).
- Бронь целиком укладывается в рабочее время **09:00–20:00 по местному времени офиса**, где стоит
  комната. Время принимается в ISO 8601 **со смещением** (`2026-11-02T10:00:00+03:00`, `...Z`,
  `...+07:00`); дата без смещения отклоняется — иначе бронь уехала бы на 3–7 часов.
- Ограничений на даты нет: брони в прошлом допустимы.
- Отменить бронь может **только её автор**.

Всё время приводится к UTC и хранится как момент времени (`timestamptz`); наружу API отдаёт UTC.
Рабочие часы считаются в часовом поясе офиса, а не в смещении, которое прислал клиент.

## API

Все методы требуют заголовки `Authorization: Bearer <токен>` и `Accept: application/json`.
Без `Accept` запрос без токена вернёт 401.

| Метод | Адрес | Что делает |
| --- | --- | --- |
| GET | `/api/bookings` | Мои брони |
| POST | `/api/bookings` | Создать бронь |
| DELETE | `/api/bookings/{booking}` | Отменить бронь |
| GET | `/api/rooms/{room}/bookings/today` | Брони комнаты на сегодня |

### Создание брони

Поле `user_id` в теле запроса **игнорируется**: автором всегда становится владелец токена
(прежний `user_id` можно не присылать).

```sh
curl -X POST http://localhost:8000/api/bookings \
  -H "Authorization: Bearer anna-token" \
  -H "Accept: application/json" \
  -H "Content-Type: application/json" \
  -d '{"room_id": 1, "title": "Планёрка", "starts_at": "2026-11-02T10:00:00+03:00", "ends_at": "2026-11-02T11:00:00+03:00"}'
```

Успех — `201` и тело брони. Ошибки — `422` в стандартном формате Laravel, с указанием поля,
которое нужно исправить:

```json
{
  "message": "Бронь не прошла валидацию.",
  "errors": {
    "starts_at": ["Бронь должна начинаться не раньше 09:00 по местному времени офиса (Europe/Moscow)."]
  }
}
```

Нарушения правил возвращаются с кодом `422` (в прежней версии конфликт возвращался как
`409 {"error": "Комната занята"}` — формат ответа об ошибках изменился). Отмена брони чужого
пользователя — `403`, отсутствие токена — `401`, несуществующая бронь — `404`.

## Одновременные запросы

Два запроса на один слот не могут создать две брони: проверка пересечения и вставка идут в одной
транзакции, которая начинается с блокировки строки комнаты (`SELECT … FOR UPDATE` по `rooms`).
Второй запрос по той же комнате ждёт коммита первого и после этого видит его бронь, поэтому
получает `422`. Разные комнаты друг друга не блокируют.

Проверено на стенде: 10 одновременных запросов на один слот дают одну бронь и девять ответов `422`.
Без блокировки те же запросы создавали девять пересекающихся броней.

Более строгий вариант — ограничение на уровне БД
(`EXCLUDE USING gist (room_id WITH =, tstzrange(starts_at, ends_at, '[)') WITH &&)` с расширением
`btree_gist`): оно запрещает пересечения независимо от кода приложения. В этом проекте не
внедрено — транзакции и блокировки достаточно для описанной модели доступа.

## Известные ограничения

- Перевод колонок времени в `timestamptz` переносит существующие строки как UTC. В чистой
  установке (`migrate:fresh --seed`) таблица пуста, поэтому проблемы нет; брони, созданные
  прежней версией кода, хранили стенное время в смещении клиента — их моменты и так были
  неверными, и пересчитать их нечем (исходное смещение не сохранялось).
- `GET /api/rooms/{room}/bookings/today` считает «сегодня» в часовом поясе сервера (UTC), а не
  офиса, и не использует индекс по времени. Метод по условию задания не переписывался — разбор в
  [`REVIEW.md`](REVIEW.md), раздел 5.
- Отсутствие перехода на летнее время в обоих офисах (смещения постоянны: +3 и +7) не требует
  отдельной обработки DST, но решение опирается на часовой пояс офиса, а не на фиксированное
  смещение — это останется верным, если появится офис в зоне с переходом на летнее время.
