# Ревью API бронирования переговорных

Разбор исходного кода `app/Http/Controllers/BookingController.php` (и связанных моделей, миграций,
маршрутов) до внесения правок. Каждый пункт проверен на работающем стенде
(Laravel 13.39, PostgreSQL 17) — не только чтением кода: запросы выполнены через `curl`, состояние
таблицы `bookings` сверено напрямую в БД, типы колонок — через `information_schema`.

Серьёзность: **critical** — данные, доступ или корректность данных под угрозой; **major** — правило
задания не выполняется или пользователь получает 500 вместо ответа; **minor** — ошибка в деталях,
которую стоит поправить, но работа при этом не ломается.

---

## 1. Краткое резюме

Пользователи жалуются на ошибки — и они правы. В `store` одновременно живут четыре класса проблем:
**небезопасная сборка SQL из пользовательского ввода**, **отсутствие авторизации** (автор брони
определяется телом запроса, а не токеном; отменять бронь может кто угодно), **неверная работа со
временем** (время хранится стенным временем в смещении клиента, рабочие часы считаются не в том
часовом поясе, в котором стоит комната) и **полное отсутствие валидации** (любой плохой ввод
превращается в 500). Отдельно: проверка пересечения использует нестрогие неравенства, поэтому
встречи «впритык» запрещены, хотя по заданию должны быть разрешены.

Что важно понимать про время: колонки `starts_at`/`ends_at` — `timestamp without time zone`, а Laravel
кладёт в них стенное время переданной строки. Клиент прислал `14:00+03:00` — в базе лежит
`2026-11-02 14:00:00`, и наружу API отдаёт это как `14:00:00.000000Z`, то есть **заявляет UTC там,
где на самом деле местное время клиента**. Момент съезжает на смещение, а два клиента, приславшие
один и тот же момент с разными смещениями, получают разные «слоты».

Итог: 4 critical, 8 major, 5 minor. Ниже — по каждому пункту.

---

## 2. Critical

### 2.1 SQL-инъекция в проверке пересечения

**Где:** `BookingController::store`, строки 23–26:

```php
$conflict = DB::select("SELECT id FROM bookings
    WHERE room_id = {$request->room_id}
    AND starts_at <= '{$request->ends_at}'
    AND ends_at >= '{$request->starts_at}'");
```

Три пользовательских значения подставляются в строку запроса как есть. `room_id`, `starts_at` и
`ends_at` приходят из тела запроса.

**Что происходит.** Значение подставляется в SQL буквально, поэтому атакующий управляет условием
`WHERE`. Проверено на стенде:

| Запрос | Результат |
| --- | --- |
| `room_id = 1`, свободный слот 26.11 10:00–11:00 | `201` — бронь создана |
| `room_id = 1`, свободный слот 27.11 10:00–11:00 | `201` — бронь создана |
| `room_id = "1 OR 1=1"`, свободный слот 28.11 10:00–11:00 | `409 «Комната занята»` |

Слот 28.11 в комнате 1 **свободен** (в комнате есть брони только на 12.11 и 25.11), но подставленное
`OR 1=1` отключило фильтр по времени: запрос нашёл любую бронь комнаты 1 и отклонил создание.
Инъекция в `starts_at` (`2026-11-14T10:00:00+03:00' OR '1'='1`) даёт постоянный 409 на любой слот.
Кроме подмены условия возможны и чтение данных, и подмена `INSERT`: значение `room_id` попадает
дальше в `Booking::create($request->all())` — при `room_id = "0 OR 1=1"` запрос падает уже на вставке
(`invalid input syntax for type bigint`).

**Как исправить.** Собрать запрос через query builder с плейсхолдерами — значения вообще не должны
попадать в текст SQL:

```php
$conflict = Booking::query()
    ->where('room_id', $roomId)
    ->where('starts_at', '<', $endsAt)
    ->where('ends_at', '>', $startsAt)
    ->exists();
```

Никаких `DB::select` со строковой интерполяцией, никаких `orderByRaw` с пользовательским вводом.
Отдельно — проверить типы и обязательность полей **до** обращения к БД (см. 3.7), потому что даже
без инъекции пустой `room_id` сейчас роняет SQL-синтаксис.

### 2.2 Автор брони определяется телом запроса, а не токеном

**Где:** `BookingController::store`, строка 37: `Booking::create($request->all())`.

`user_id` входит в `#[Fillable]` модели `Booking`, поэтому значение из тела запроса попадает в
колонку как есть. Токен при этом полностью игнорируется: `$request->user()` в `store` не используется.

**Что происходит.** Проверено: запрос с токеном Анны (`anna-token`) и `"user_id": 2` создал броню,
принадлежащую Борису:

```json
{"room_id":1,"user_id":2,"title":"X","starts_at":"2026-11-02T10:00:00.000000Z", ...}
```

В таблице — строка с `user_id = 2`. Любой аутентифицированный пользователь может создавать брони
от чужого имени, а чужую бронь — ещё и отменить (см. 2.3). Это же делает API бессмысленным: клиент
обязан знать свой `id` и подставлять его руками.

**Как исправить.** Автора брать только из аутентифицированного пользователя, а поле из тела запроса
игнорировать:

```php
$booking = Booking::create([
    'room_id' => $validated['room_id'],
    'user_id' => $request->user()->id,
    // ...
]);
```

Создание через `FormRequest` даёт это автоматически: `validated()` не содержит `user_id`, если его
не просили в правилах. Присланный `user_id` при этом лучше **игнорировать**, а не отвергать —
старые клиенты, которые его шлют, продолжат работать.

---

### 2.3 Отменить бронь может кто угодно

**Где:** `BookingController::destroy`, строки 45–49:

```php
public function destroy($id)
{
    Booking::findOrFail($id)->delete();

    return response()->noContent();
}
```

Автор не проверяется вообще.

**Что происходит.** Проверено: DELETE с токеном Бориса (`boris-token`) удалил бронь Анны —
ответ `204`, а в таблице по `id = 1` не осталось ни одной строки. Любой пользователь может
удалить чужую встречу — включая встречу в чужом офисе.

**Как исправить.** Проверять владельца и отвечать понятной ошибкой:

```php
if ($booking->user_id !== $request->user()->id) {
    throw new AuthorizationException('Отменить бронь может только её автор.');
}
```

`AuthorizationException` Laravel отдаёт как `403` с этим сообщением. Дополнительно стоит перейти на
привязку модели (`destroy(Booking $booking)` + маршрут `/bookings/{booking}`): тогда отсутствующая
бронь даёт `404` без ручного `findOrFail`.

### 2.4 Время хранится стенным временем клиента, а не моментом

**Где:** миграция `2026_10_29_000003_create_bookings_table.php` (`$table->timestamp('starts_at')` —
`timestamp without time zone`) и `BookingController::store`, где `Booking::create($request->all())`
получает строку из тела запроса.

**Что происходит.** Laravel приводит дату к формату `Y-m-d H:i:s` без перевода в другой пояс, поэтому
в наивную колонку попадает стенное время той зоны, которую указал клиент. Проверено:

| Вход | В таблице `starts_at` | В ответе API |
| --- | --- | --- |
| `2026-11-02T10:00:00+03:00` | `2026-11-02 10:00:00` | `2026-11-02T10:00:00.000000Z` |

Столбец наивный, значение — местное время клиента, а ответ утверждает, что это UTC (`Z`).
Фактический момент (07:00Z) отличается от заявленного на 3 часа. Последствия:

- два клиента, приславшие **один и тот же момент** разными смещениями (`10:00+07:00` и `03:00+03:00`),
  получают в базе `10:00` и `03:00` — то есть два разных слота для одного момента;
- сравнение с рабочим временем и проверка пересечения сравнивают стенные часы разных зон;
- любая выгрузка или внешний потребитель данных трактует значения неверно.

**Как исправить.** Нормализовать время один раз, на входе, и хранить настоящий момент:

1. на входе принимать ISO 8601 **со смещением** и приводить к UTC (`CarbonImmutable::parse($v)->utc()`);
2. перевести колонки в `timestamptz` (`$table->timestampTz('starts_at')`) — тогда БД хранит момент,
   а не стенные часы;
3. зафиксировать часовой пояс сессии Postgres (`'timezone' => 'UTC'` в `config/database.php`),
   иначе наивная строка, которую Laravel отправляет в `timestamptz`, будет прочитана по TZ сервера
   (сейчас это `Etc/UTC`, но это свойство окружения, а не зафиксированное намерение).

## 3. Major

### 3.1 «Впритык» считается пересечением

**Где:** `store`, строки 25–26: `starts_at <= '…' AND ends_at >= '…'`.

**Что происходит.** Проверено: после брони 10:00–11:00 запрос 11:00–12:00 в ту же комнату получил
`409 «Комната занята»». По заданию встречи «впритык» разрешены: 10:00–11:00 и 11:00–12:00 — это не
пересечение. Из-за `<=` и `>=` любая бронь, касающаяся границы другой, считается конфликтом —
половина нормального расписания не бронируется.

**Как исправить.** Сравнивать интервалы строго: пересечение есть, только если
`starts_at < other.ends_at AND ends_at > other.starts_at`. Граничные касания при этом не конфликтуют.

---

### 3.2 Рабочее время считается в смещении запроса, а не в часовом поясе офиса

**Где:** `store`, строки 32–35:

```php
$start = Carbon::parse($request->starts_at);
if ($start->hour < 9 || $start->hour >= 20) { ... }
```

Часовой пояс офиса (`office.timezone`, `Europe/Moscow` / `Asia/Novosibirsk`) не используется вообще.

**Что происходит.** Проверено: комната в Новосибирске, бронь на 11:00 **местного** времени,
присланная как `07:00+03:00` (это тот же момент), получила `422 «Нерабочее время»` — потому что
проверка посмотрела на час `7` в смещении запроса. Симметрично: бронь на 21:00 по Новосибирску,
присланная как `14:00+03:00`, прошла бы как «рабочее время», хотя 21:00 в офисе закрыто.

**Как исправить.** Взять зону из офиса комнаты и перевести в неё:

```php
$localStart = $start->copy()->setTimezone($room->office->timezone);
$localEnd = $end->copy()->setTimezone($room->office->timezone);
```

и проверять границы 09:00–20:00 уже в `$localStart`/`$localEnd`. Время, которое прислал клиент,
должно влиять только на момент, а не на то, «какой час там у офиса».

---

### 3.3 Конец брони не проверяется

**Где:** `store`, строки 33–35 — проверяется только `$start->hour`, `$end` не смотрится вовсе.

**Что происходит.** Проверено: бронь `19:30–21:00` в московской комнате создана с ответом `201`,
хотя рабочий день заканчивается в 20:00.

**Как исправить.** Проверять обе границы в локальном времени офиса: начало не раньше 09:00,
конец не позже 20:00, и обе точки — в пределах одного рабочего дня.

---

### 3.4 Длительность брони не ограничена

**Где:** `store` — проверки длительности нет вовсе.

**Что происходит.** Проверено: бронь на 5 минут (`10:00–10:05`) создана с ответом `201`. По заданию
длительность — от 15 минут до 4 часов.

**Как исправить.** Считать длительность в секундах и проверять диапазон включительно:
`900 <= ends_at - starts_at <= 14400`. Проверку `ends_at > starts_at` сделать отдельной (см. 3.6) —
иначе отрицательная длительность «провалится» в этот диапазон.

---

### 3.5 Шаг 15 минут не проверяется

**Где:** `store` — проверки нет.

**Что происходит.** Проверено: бронь `10:07–11:07` создана с ответом `201`. По заданию время
должно быть кратно 15 минутам (10:00, 10:15, …). Из-за этого расписание перестаёт быть пригодным
для отображения сеткой.

**Как исправить.** Проверять, что минуты начала и конца кратны 15 (и секунд нет) — в локальном
времени офиса, как и остальные правила времени.

---

### 3.6 `ends_at` может быть раньше `starts_at`

**Где:** `store` — проверки нет.

**Что происходит.** Проверено: бронь `10:00–09:00` создана с ответом `201`, и в таблице лежит
строка, у которой конец раньше начала. Такая строка не имеет смысла и ломает любые расчёты
пересечений (в том числе приведённые выше).

**Как исправить.** Проверять `ends_at > starts_at` до всех остальных проверок времени и отдавать
ошибку с указанием поля `ends_at`.

---

### 3.7 Нет валидации: плохой ввод даёт 500

**Где:** `store` — валидации нет; `Booking::create($request->all())` отдаёт в БД что угодно.

**Что происходит.** Три разных 500 на трёх разных ошибках ввода:

| Ввод | Ответ |
| --- | --- |
| нет `room_id` | `500`, `SQLSTATE[42601]: syntax error at or near "AND"` — оборвавшийся SQL-запрос |
| `room_id = 999` (нет такой комнаты) | `500`, `SQLSTATE[23503]: Foreign key violation` |
| нет `user_id` | `500`, `SQLSTATE[23502]: Not null violation ... column "user_id"` |

Пользователь не может понять, что именно он сделал не так, и видит стек-трейс вместо ответа.

**Как исправить.** Валидировать вход до обращения к БД: `FormRequest` с правилами
`room_id: required|integer|exists:rooms,id`, `title: required|string|max:255`, даты — отдельным
правилом ISO 8601 со смещением. Ответ — `422` с понятным текстом и указанием поля.

---

### 3.8 Гонка при одновременных запросах

**Где:** `store` — проверка конфликта и вставка идут двумя отдельными обращениями к БД, без транзакции
и без блокировок.

**Что происходит.** Между `SELECT` (проверка) и `INSERT` есть окно, в котором второй запрос
успевает вставить пересекающуюся бронь: оба проверяют конфликт, оба видят пустоту, оба вставляют —
получается двойная бронь на один слот.

**Как исправить.** Проверку и вставку выполнять в одной транзакции, закрывая строку комнаты:

```php
DB::transaction(function () use (...) {
    Room::query()->whereKey($roomId)->lockForUpdate()->first();

    // проверка конфликта
    // вставка
});
```

`SELECT … FOR UPDATE` по строке комнаты выстраивает одновременные запросы по этой комнате в очередь:
второй дождётся коммита первого и увидит его бронь. Разные комнаты друг друга не блокируют.
Более строгий вариант — ограничение на уровне БД
(`EXCLUDE USING gist (room_id WITH =, tstzrange(starts_at, ends_at, '[)') WITH &&)`), но оно требует
расширения `btree_gist` и своей обработки ошибки БД — в текущем объёме задачи транзакции достаточно.

## 4. Minor

### 4.1 `Log::withContext()` не доходит до канала `bookings`

**Где:** `store`, строки 39–40:

```php
Log::withContext(['booking_id' => $booking->id]);
Log::channel('bookings')->info('Booking created');
```

`withContext()` добавляет контекст в канал **по умолчанию**, а логи пишет **канал `bookings`** — это
разные экземпляры Monolog. Проверено: в `storage/logs/bookings.log` лежит
`local.INFO: Booking created` — без `booking_id`, хотя в коде он «приклеивается» двумя строками выше.

**Как исправить.** Передать контекст в сам вызов:
`Log::channel('bookings')->info('Booking created', ['booking_id' => $booking->id])`.

---

### 4.2 Без `Accept: application/json` — 500 вместо 401

**Где:** не в контроллере, а в конфигурации приложения: `Illuminate\Auth\Middleware\Authenticate`
вызывает `route('login')` для запросов, которым не нужен JSON, а маршрута `login` в приложении нет.

**Что происходит.** Проверено: `GET /api/bookings` без токена и без `Accept` → `500
«Route [login] not defined»` вместо `401`. Это зафиксировано и в README проекта как «особенность».

**Как исправить.** Сказать Laravel, что перенаправлять гостя некуда:
`$middleware->redirectGuestsTo(fn () => null)` в `bootstrap/app.php`. Тогда обработчик отдаёт `401`,
а для API — JSON (в `bootstrap/app.php` уже есть `shouldRenderJsonWhen` для путей `api/*`).

---

### 4.3 Формат ошибок разнородный

**Где:** `store` отдаёт `response()->json(['error' => 'Комната занята'], 409)`, а валидация Laravel
даёт `{"message": …, "errors": {поле: […]}}`.

**Что происходит.** Клиенту приходится разбирать два формата. Плюс код `409` в задании не
оговорен — там явно указан `422` для ошибок валидации.

**Как исправить.** Единый формат `422` со стандартной структурой Laravel
(`message` + `errors` по полям) для всех нарушений правил; ошибка «комната занята» — это тоже
нарушение правила, поэтому `422` с ключом `starts_at`.

---

### 4.4 Наружу отдаётся вся модель

**Где:** `store` возвращает `Booking::create(...)` — Laravel сериализует модель целиком.

**Что происходит.** В ответе видны `user_id`, `created_at`, `updated_at` и всё прочее — клиенту это
не нужно, а форма ответа не описана нигде. `index` отдаёт модель же, так что сейчас это хотя бы
консистентно.

**Как исправить.** Либо ресурс-сериализатор с фиксированным набором полей, либо (дешевле) явный
`response()->json($booking, 201)` с тем же набором. В объём задачи ресурсы не входят.

---

### 4.5 Нет ограничения длины `title`

**Где:** `store` — валидации нет; колонка `title` — `varchar(255)`.

**Что происходит.** Слишком длинный заголовок упирается в ограничение БД → `500` вместо `422`.

**Как исправить.** Правило `max:255` в валидации (см. 3.7).

## 5. Разбор `index` и `today` (по заданию не исправляются)

### 5.1 `today` считает «сегодня» в часовом поясе сервера, а не офиса

`whereDate('starts_at', today())` — `today()` берётся в TZ приложения (`UTC`), а не в TZ офиса.
Между 17:00 и 24:00 UTC для новосибирского офиса уже наступило «сегодня», а метод вернёт вчерашний
день: смещение между офисами и сервером не учитывается.

### 5.2 `whereDate` не использует индекс по времени

`whereDate` оборачивает колонку в `DATE(...)`, индекс по `starts_at` перестаёт использоваться. На
текущих объёмах незаметно, на большем расписании — полный просмотр таблицы.

### 5.3 `today` отдаёт время строкой без часового пояса

`$b->starts_at . ' – ' . $b->ends_at` даёт `"2026-11-02 14:00:00 – 15:00:00"`. Что это за время и в
какой зоне — из ответа не понять, в отличие от `index`, где время сериализуется ISO-строкой.

### 5.4 Суффикс `Z` в ответах — ложь

`index` и `store` отдают время как `2026-11-02T14:00:00.000000Z`, то есть **заявляют UTC**, хотя в
базе лежит стенное время клиента (см. 2.4). Для клиента это выглядит как корректный UTC-время и
вводит в заблуждение при расчёте пересечений на своей стороне.

### 5.5 `index` в остальном корректен

`where('user_id', $request->user()->id)` — свои брони, `paginate(20)` — разумная страница,
`orderByRaw('starts_at DESC')` — константа. Метод править не нужно, кроме оговорённых пунктов.

## 6. Выглядит подозрительно, но проблемой не является

### 6.1 `orderByRaw('starts_at DESC')`

Выглядит как «сырой SQL — значит инъекция». Здесь это не так: строка — константа, пользовательского
ввода в ней нет. Менять на `orderBy('starts_at', 'desc')` — вопрос вкуса и единообразия, а не
безопасности.

### 6.2 `#[Fillable]` действительно ограничивает масс-присваивание

Масс-присваивание выглядит подозрительно, но атрибут `#[Fillable]` работает: записать в бронь
произвольные поля (`id`, `created_at`, поля других таблиц) нельзя. Проблема не в самом механизме, а
в том, что `user_id` в списке разрешённых (см. 2.2).

### 6.3 В обоих офисах нет перехода на летнее время

`Europe/Moscow` и `Asia/Novosibirsk` перешли на постоянные смещения (+3 и +7) — переходов на летнее
время в них нет (проверено `DateTimeZone::getTransitions()` за 2026 год: единственный переход —
начало диапазона, смещения не меняются). Это хорошо: правило рабочего времени стабильно, а «час
перехода» не может породить бронь, которая выглядит нормальной, но попадает в нерабочее время.
Оговорка: решение должно опираться на **часовой пояс офиса**, а не на фиксированное смещение — тогда
оно останется верным, если появится офис в зоне с переходом на летнее время.

### 6.4 Канал `bookings` в конфигурации есть и работает

Канал настроен верно и пишет в `storage/logs/bookings.log`. Проблема не в канале, а в том, как в него
передаётся контекст (см. 4.1).

### 6.5 `Booking::create()` возвращает 201

Ответ `201 Created` для только что созданной модели — штатное поведение Laravel, а не баг. Вопрос
лишь в том, какие поля уходят в ответ (см. 4.4).

### 6.6 `index` фильтрует по `user_id` — правильно

Метод отдаёт только брони текущего пользователя; авторизация здесь не нарушена. Нарушена она в
`store` и `destroy`.

## 7. Что сознательно не трогаем

| Что | Почему |
| --- | --- |
| `index`, `today` | Прямое требование задания: «исправлять не нужно, их достаточно разобрать в ревью». Разбор — в разделе 5. |
| Версионирование API, ресурсы-сериализаторы | Не требуются заданием; формат ответа сейчас и так меняется (см. 4.3) — менять его целиком незачем. |
| Rate limiting | Не требуется заданием; отдельная задача для продакшена. |
| Ограничения на даты (нельзя бронировать в прошлом) | Задание прямо говорит: «других ограничений на даты нет». |
| Порядок брони по офисам, перенос между офисами | Не описан в задании. |

## 8. Порядок исправления (реализован в истории коммитов)

1. Ревью (этот файл) — фиксируем, что именно чиним.
2. Доменные правила брони в отдельном сервисе: длительность, шаг, рабочее время офиса, пересечение.
3. Валидация входа (`FormRequest`) и HTTP-контракт: `422` с указанием поля, `user_id` из токена.
4. Отмена брони только автором: `403` вместо молчаливого удаления.
5. Защита от гонки: транзакция и блокировка строки комнаты.
6. Время как момент: `timestamptz` и фиксированный TZ сессии Postgres.
