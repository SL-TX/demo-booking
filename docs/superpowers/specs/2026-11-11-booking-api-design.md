## 1. Зачем

Пользователи жалуются на ошибки в API бронирования (`app/Http/Controllers/BookingController.php`,
написанное предыдущим разработчиком). Требуется:

2. **Часть 2** — довести `store` и `destroy` до правил из задания, с feature-тестами на каждое правило.
3. **Часть 3** — `AI_NOTES.md`: какие инструменты использовались, где ИИ ошибся, что проверялось вручную.

Плюс: README с запуском и тестами в одну-две команды, осмысленная история коммитов.

Окружение: `docker compose up -d --wait` → Laravel 13.39.0, PostgreSQL 17, PHP 8.4.
Стенд поднят, база засеяна, API проверен запросами `curl` и запросами в БД.

## 3. Цели, не-цели, анти-цели

**Цели**
- `store` и `destroy` выполняют все правила задания и отдают понятные ошибки.
- Время в системе — однозначный момент времени; рабочее время считается в часовом поясе офиса комнаты.
- Каждое правило закрыто feature-тестом.
- `REVIEW.md`, `AI_NOTES.md`, README — по заданию.
- История коммитов показывает ход решения, а не один дамп.

**Не-цели**
- `index` и `today` не переписываются (по заданию) — но разбираются в `REVIEW.md`.
- Нет версионирования API, нет ресурсов-сериализаторов, нет rate limiting, нет пагинации в `store`.
- Нет ограничений на даты («Других ограничений на даты нет»): брони в прошлом разрешены.

**Анти-цели (что считается провалом, даже если работает)**
- Возврат 500 на пользовательский ввод вместо 422.
- Проверка правил, зависящая от того, как клиент «случайно» прислал смещение.
- «Впритык» считается конфликтом.
- Правила, написанные прямо в контроллере вперемешку с HTTP-логикой и без тестов.
- Мёртвый или декоративный код (например, `Log::withContext`, который ничего не делает).

## 4. Ограничения

- Стек и зависимости не меняем (`AGENTS.md`/задание: PHP 8.4, Laravel 13, PostgreSQL). Новых пакетов не добавляем.
- Модели и миграции менять можно (прямо разрешено заданием).
- `room_id` в запросе — идентификатор комнаты; `user_id` в запросе больше не имеет значения.
- Оба офиса — фиксированный набор часовых поясов без DST, но решение не должно зависеть от этого.

## 5. Рассмотренные подходы

### 5.1 Где живут правила

| Вариант | Плюсы | Минусы |
| --- | --- | --- |
| **A. Всё в контроллере** (как сейчас) | ноль новых файлов | контроллер обрастает правилами; правила нельзя вызвать из другого места; тесты бьют по HTTP ради проверки домена |
| **B. FormRequest (форма входа) + сервис (правила брони)** ← **выбран** | форма и доменные правила разделены; доменные правила тестируются и переиспользуются; контроллер тонкий; ошибки 422 с полями «из коробки» | появляется 2–3 новых класса |
| **C. Правила на модели `Booking`** | идиоматично для Eloquent | правила завязаны на офис и чужую таблицу, в модели это шум; проверка конфликта всё равно не в модели |

Выбран **B**. `StoreBookingRequest` отвечает за «форма входа» (обязательность, типы, формат даты,
существование комнаты), сервис — за правила брони (длительность, шаг, рабочее время, конфликт)
и за атомарность записи.

### 5.2 Как хранить время

| Вариант | Плюсы | Минусы |
| --- | --- | --- |
| **A. Оставить `timestamp`, писать UTC** | без миграции | колонка не хранит момент — только «стенные часы»; любая будущая SQL-выборка обязана знать про UTC; смешение с наивными `created_at` |
| **B. `timestampTz` (`timestamptz`) + нормализация в UTC** ← **выбран** | БД хранит настоящий момент; сравнения в SQL корректны по построению; `whereDate` в `today()` разрешается в TZ сессии | нужна миграция; старые (испорченные) значения трактуются как UTC |

Выбран **B**. Проверено на стенде: `timestamptz` + строгое сравнение интервалов даёт корректное
поведение «впритык не конфликтует», `whereDate` по `timestamptz` возвращает дату UTC-сессии.

Ключевой приём: **на вход** ISO 8601 со смещением приводится к UTC (`CarbonImmutable::parse($v)->utc()`),
**в БД** лежит `timestamptz` (момент), **рабочее время** считается через `->setTimezone($office->timezone)`.

### 5.3 Как закрыть гонку (бонус)

| Вариант | Плюсы | Минусы |
| --- | --- | --- |
| **A. Транзакция + `SELECT … FOR UPDATE` по строке комнаты** ← **выбран** | просто, переносимо, легко объяснить; сериализует все брони по комнате | защищает только от гонок внутри этого приложения |
| **B. Ограничение `EXCLUDE USING gist (room_id WITH =, tstzrange(starts_at, ends_at, '[)') WITH &&)`** | гарантия на уровне БД, не обойти никаким кодом | нужна `btree_gist`, свои SQL-ошибки (23P01) надо отображать в 422; заметно сложнее объяснить |
| **C. Только описать в README** | разрешено заданием | гонка остаётся |

Выбран **A**, вариант **B** описывается в README как следующий уровень защиты.
Транзакция + блокировка комнаты даёт инвариант «в один момент в комнате одна бронь» для любых двух
одновременных запросов к этой комнате: второй запрос встанет в очередь на `FOR UPDATE` и после
коммита первого увидит его бронь в проверке конфликта.

### 5.4 Формат ошибок

`422` со стандартной формой Laravel: `{"message": "…", "errors": {"starts_at": ["…"]}}`.
Отдельного `409` не будет: **по решению заказчика все нарушения правил возвращают 422**
(в задании явно указан только 422). Отмена чужой брони — `403`.

Это **ломающее изменение контракта**: сегодня конфликт — это `409 {"error": "Комната занята"}`.
Клиенты, читающие ключ `error` или код `409`, сломаются. Совместимость сохраняется только для
`user_id` в теле запроса (игнорируется, а не отвергается). Изменение контракта фиксируется в README.

### 5.5 Инвариант часового пояса БД

Laravel отправляет даты в БД как наивные строки `Y-m-d H:i:s`, и Postgres трактует их в **часовом
поясе сессии**. Сейчас это `Etc/UTC` — но так получилось потому, что так настроен сервер, а не потому,
что это зафиксировано в репозитории (`config/database.php` не задаёт `timezone` для `pgsql`).

Чтобы инвариант «в БД лежит момент времени» не зависел от окружения, в конфигурацию соединения
добавляется `'timezone' => 'UTC'` — `PostgresConnector::configureTimezone()` выполнит
`set time zone 'UTC'` при подключении. Дополнительно код нормализует значения в UTC в двух местах
(сервис и скоуп конфликта), поэтому не-UTC `Carbon` физически не может попасть в SQL-сравнение
в неверной интерпретации — это ровно тот класс ошибок, который мы чиним.

## 6. Контракт API (итоговый)

### 6.1 `POST /api/bookings`

Запрос:

```json
{
  "room_id": 1,
  "title": "Планёрка",
  "starts_at": "2026-11-02T10:00:00+03:00",
  "ends_at": "2026-11-02T11:00:00+03:00"
}
```

- `user_id` в теле запроса **игнорируется** (автор = владелец токена). Старые клиенты, которые
  присылали `user_id`, продолжают работать.
- `starts_at`/`ends_at` — ISO 8601 **со смещением**: `+03:00`, `+0300`, `Z`, `+07:00`; секунды и
  доли секунды опциональны; разделитель `T` или пробел. Дата без смещения — 422 («укажите часовой пояс»),
  потому что «молчаливое» предположение UTC сдвигает бронь на 3–7 часов.
- Успех: `201`, тело — модель брони (как сейчас: `id`, `room_id`, `user_id`, `title`, `starts_at`,
  `ends_at`, `created_at`, `updated_at`).
- Ошибка: `422`, `{"message": "…", "errors": {поле: [сообщения]}}`.

### 6.2 `DELETE /api/bookings/{booking}`

- `204` — автор отменил свою бронь.
- `403` — бронь принадлежит другому: `{"message": "Отменить бронь может только её автор."}`.
- `404` — брони с таким id нет.

### 6.3 Правила и сообщения

| Правило | Где проверяется | Ключ в `errors` | Сообщение |
| --- | --- | --- | --- |
| `room_id` обязателен, целый, существует | FormRequest | `room_id` | «Укажите комнату.» / «Комната с таким id не найдена.» |
| `title` обязателен, строка, ≤ 255 | FormRequest | `title` | «Укажите название встречи.» / «Название не длиннее 255 символов.» |
| Формат даты ISO 8601 со смещением | FormRequest | `starts_at` / `ends_at` | «Укажите время в формате ISO 8601 со смещением, например 2026-11-02T10:00:00+03:00.» |
| `ends_at` > `starts_at` | сервис | `ends_at` | «Время окончания должно быть позже времени начала.» |
| Длительность 15 мин … 4 ч (включительно) | сервис | `ends_at` | «Длительность брони — от 15 минут до 4 часов.» |
| Начало кратно 15 минутам | сервис | `starts_at` | «Время начала должно быть кратно 15 минутам.» |
| Конец кратен 15 минутам | сервис | `ends_at` | «Время окончания должно быть кратно 15 минутам.» |
| Начало раньше 09:00 местного | сервис | `starts_at` | «Бронь должна начинаться не раньше 09:00 по местному времени офиса (Europe/Moscow).» |
| Конец позже 20:00 местного | сервис | `ends_at` | «Бронь должна заканчиваться не позже 20:00 по местному времени офиса (Europe/Moscow).» |
| Бронь переходит на следующий день | сервис | `ends_at` | «Бронь должна целиком помещаться в один рабочий день офиса.» |
| Нет пересечения с другой бронью той же комнаты | сервис | `starts_at` | «Комната занята в это время.» |
| Автор | сервис (`destroy`) | — (403) | «Отменить бронь может только её автор.» |

Принцип: в `errors` попадает то поле, которое клиент должен изменить, чтобы правило выполнилось.
Правила **не** прерываются на первом нарушении — сервис собирает все нарушения и отдаёт их одним
`ValidationException::withMessages()`, поэтому в ответе может быть несколько ключей сразу.

Границы: 09:00–09:15 и 19:45–20:00 — валидны; 08:45, 20:15, бронь через полночь — нет.

### 7.2 Схема времени

- Миграция переводит `starts_at`, `ends_at` в `timestampTz` (`timestamptz`).
- `created_at`/`updated_at` остаются `timestamp` (служебные, всегда UTC).
- Значения нормализуются **до** записи: `CarbonImmutable::parse($iso)->utc()`. Нормализация
  повторяется в сервисе и в скоупе конфликта (`->utc()`), чтобы не-UTC значение физически не могло
  попасть в SQL-сравнение в неверной интерпретации.
- Часовой пояс сессии БД фиксируется в `config/database.php` (`'timezone' => 'UTC'` для `pgsql`) —
  иначе «наивная» строка, которую Laravel отправляет в `timestamptz`, трактуется по TZ сервера.
- Существующие строки приводятся Postgres из `Etc/UTC` — в свежей установке таблица пуста
  (сидер брони не создаёт), поэтому миграция ничего не искажает. Старые значения в любом случае
  были некорректны (см. §2) — это отражено в `REVIEW.md`.

### 7.3 Правила в сервисе

Проверки выполняются **все**, а не до первого нарушения: результаты собираются в массив
`[поле => [сообщения]]`, и если он непуст — выбрасывается один `ValidationException::withMessages()`.

1. `ends_at > starts_at` → `ends_at`.
2. Длительность: `900 с ≤ Δ ≤ 14400 с` → `ends_at`.
3. Кратность 15 минутам: `minute % 15 === 0` и `second === 0` **в местном времени офиса** (для
   смещений +3/+7 совпадает с UTC, но правило должно быть локальным по смыслу) → `starts_at` и/или `ends_at`.
4. Рабочее время: `localStart >= 09:00:00`, `localEnd <= 20:00:00`, `localStart->toDateString() === localEnd->toDateString()`
   → `starts_at` (начало раньше 09:00), `ends_at` (конец позже 20:00 или переход на следующий день).
   Обе границы проверяются по **часовому поясу офиса комнаты**, а не по смещению запроса.
5. Конфликт: строгое пересечение интервалов в той же комнате → `starts_at`.

Проверки 1–4 — чистые вычисления, проверка 5 — запрос к БД.

### 7.4 Атомарность

```php
DB::transaction(function () use (...) {
    Room::query()->whereKey($roomId)->lockForUpdate()->firstOrFail();
    // проверки 1–5
    return Booking::create([... 'user_id' => $user->id ...]);
});
```

`lockForUpdate()` → `SELECT … FOR UPDATE` на строке комнаты. Второй одновременный запрос по той же
комнате блокируется на этой строке до коммита первого, после чего его проверка конфликта увидит
чужую бронь. Проверка конфликта и вставка — в одной транзакции, поэтому «проверил — записал» не
расходится.

Ограничение схемы: сериализуются брони **по комнате**, не по всей таблице. Разные комнаты
не блокируют друг друга.

### 7.5 Скоуп конфликта

```php
public function scopeConflicting(Builder $query, int $roomId, CarbonInterface $startsAt, CarbonInterface $endsAt): Builder
{
    return $query->where('room_id', $roomId)
        ->where('starts_at', '<', $startsAt->utc())     // ← нормализация здесь и в ends_at
        ->where('ends_at', '>', $endsAt->utc());
}
```

Строгие неравенства: интервалы `[10:00, 11:00)` и `[11:00, 12:00)` не пересекаются — «впритык»
разрешён, как требует задание.

### 7.6 Авторизация

- `store`: `user_id` берётся только из аутентифицированного пользователя; поле из тела запроса
  в `validated()` не попадает, поэтому масс-присваивание не может его подменить.
- `destroy`: `AuthorizationException` → 403, если `$booking->user_id !== $user->id`.
- Связывание модели: `destroy(Booking $booking)` + маршрут `/bookings/{booking}` (форма URL не меняется).

### 7.7 Логирование

`Log::channel('bookings')->info('Booking created', ['booking_id' => $booking->id, 'room_id' => …, 'user_id' => …])`
— контекст передаётся в канал напрямую (текущий `Log::withContext()` до канала не доходит).

### 7.8 Неавторизованный запрос без `Accept`

`Authenticate::unauthenticated()` вызывает `route('login')`, когда запрос не `expectsJson()` — маршрута
`login` в приложении нет → 500. Лечится `->withMiddleware(fn (Middleware $m) => $m->redirectGuestsTo(fn () => null))`:
тогда `redirectTo` = null, обработчик отдаёт 401 (для API — JSON, т.к. в `bootstrap/app.php` уже есть
`shouldRenderJsonWhen(fn ($r) => $r->is('api/*') || $r->expectsJson())`).

### 8.4 `tests/Feature/BookingConcurrencyTest.php` (бонус)

Использует `DatabaseMigrations` (не `RefreshDatabase`): данные должны быть **закоммичены**, чтобы
вторая сессия Postgres их видела.

- Вторая сессия создаётся на лету: копия конфигурации `pgsql` под другим именем
  (`config(['database.connections.pgsql_alt' => …])` + `DB::purge('pgsql_alt')`), сервис при этом
  работает через соединение по умолчанию — его сигнатура не меняется.
- Сессия A: `BEGIN;` + `SELECT … FROM rooms WHERE id = X FOR UPDATE` — держит блокировку комнаты.
- Сессия B (соединение по умолчанию): `SET lock_timeout = 250ms`, затем `BookingService::create()`
  для того же слота. Ожидание: сервис **встаёт на блокировку комнаты** и падает с
  `SQLSTATE 55P03` (lock timeout), ничего не вставив.
- Что это доказывает: блокировка комнаты берётся **до** проверки конфликта и удерживается до конца
  транзакции, поэтому второй пишущий не может вклиниться между «проверил» и «записал».
- Чего тест не доказывает: что второй запрос после ожидания увидит чужую бронь и получит 422 —
  для этого нужны два процесса. Это проверяется **вручную** на стенде: N параллельных `curl`
  на один слот дают ровно одну бронь и N−1 ответов 422 (результат — в `AI_NOTES.md`).

Существующий `tests/Feature/BookingIndexTest.php` продолжает проходить без правок.

## 9. Документы

- **`REVIEW.md`** — таблица/списком: проблема, серьёзность, как исправить; отдельно раздел
  «выглядит подозрительно, но проблемой не является» (`orderByRaw` с константой; `#[Fillable]`
  как ограничение масс-присваивания; отсутствие DST в обоих офисах; `index`/`today` — что в них
  не так и почему не чинили). Также: почему `index`/`today` не трогаем и что в них сломано:
  - `today` считает «сегодня» в часовом поясе сервера (UTC), а не офиса; между 17:00 и 24:00 UTC
    «сегодня» офиса уже наступает, а ответ ещё за вчера;
  - `whereDate('starts_at', …)` не использует индекс по `starts_at` (проверка на `starts_at` + `ends_at`);
  - `today` отдаёт время строкой `"2026-11-02 14:00:00 – 15:00:00"` — **без часового пояса**, его
    нельзя интерпретировать однозначно;
  - `index`/`store` отдают время с суффиксом `Z`, то есть **заявляют UTC**, хотя фактически там
    местное стенное время клиента. Суффикс `Z` — ложь; после перехода на `timestamptz` он станет
    правдой.
- **`AI_NOTES.md`** — по трём пунктам задания: инструменты и 2–3 ключевых промпта дословно;
  где ИИ ошибся и как это заметили (кандидаты: `Log::withContext`, «не пересекаются» vs
  «впритык», `timestamptz` vs наивные `timestamp`); что проверялось вручную (стенд, `curl`, SQL-запросы
  к БД, чтение исходников Laravel 13 в `vendor/`) и что сознательно не отдано ИИ.
- **`README.md`** — запуск и тесты в одну-две команды; изменённый пример `curl` (без `user_id`);
  контракт ошибок (422/403/401); описание модели конкурентности (транзакция + `FOR UPDATE`)
  и альтернативы в виде `EXCLUDE`-ограничения; ссылка на `REVIEW.md`.

## 10. История коммитов

Порядок выбран так, чтобы **каждый коммит оставался рабочим и не менял смысл данных**:

1. `Ревью API бронирования` — `REVIEW.md` (анализ исходного кода, до правок).
2. `Валидация входа брони` — `StoreBookingRequest` + `Iso8601WithOffset` + тесты на 422.
3. `Правила брони: длительность, шаг, рабочее время` — `BookingService` + тесты.
4. `Конфликт брони и защита от гонки` — скоуп `scopeConflicting`, транзакция + `FOR UPDATE`, тест на блокировку.
5. `Контроллер: store и destroy по правилам` — `BookingController`, маршрут `{booking}`,
   `bootstrap/app.php`, логирование, тесты на 403/204/401.
6. `Время брони: моменты вместо наивных таймстемпов` — миграция на `timestamptz` + `'timezone' => 'UTC'`
   в `config/database.php`.
7. `Документы задания` — `AI_NOTES.md`, обновление `README.md`.

Почему миграция типа колонок идёт **после** кода, а не до: пока контроллер пишет наивное стенное
время клиента, смена типа колонки заставила бы Postgres переинтерпретировать его как UTC и сдвинула
бы все брони на смещение клиента. Сначала код начинает писать UTC (шаги 2–5) — и только потом
меняется тип колонки (шаг 6): на этом шаге данные уже корректны и миграция их не искажает.

Коммиты идут по ходу работы и отражают ход рассуждения, а не финальный дамп.

## 11. Решения, принятые нами (проверьте)

Решения, которые нужно было принять «заказчику» (заданы вопросом и подтверждены):

- **422** на все нарушения правил (включая конфликт), **403** на отмену чужой брони — **решено заказчиком**.
- Ломающее изменение контракта ошибок (было `409 {"error": …}` → стало `422 {"message": …, "errors": …}`)
  фиксируется в README.

Решения, принятые нами (застройщик может пересмотреть, но они не меняют объём работы):

- Ключи в `errors` — по тому полю, которое клиент должен изменить (таблица §6.3); все нарушения
  собираются и отдаются одним 422, а не по одному.
- `user_id` из тела запроса игнорируется, а не отвергается (совместимость со старыми клиентами).
- Дата без смещения отвергается (422), а не трактуется как UTC.
- `timestamptz` вместо наивного `timestamp` + `'timezone' => 'UTC'` для соединения `pgsql` —
  сознательная миграция схемы и конфигурации.
- Нормализация в UTC повторяется в сервисе и в скоупе — «защита в глубину» против повторения
  исходной ошибки.
- Гонка закрывается транзакцией + `FOR UPDATE`; `EXCLUDE`-ограничение описано в README как
  следующий уровень, но не внедряется.
- Тест на гонку детерминированный (таймаут блокировки), а сквозная проверка «N параллельных запросов →
  одна бронь» делается вручную на стенде и попадает в `AI_NOTES.md`.
- `APP_DEBUG=false` в `phpunit.xml`, чтобы тело ошибки в тестах совпадало с контрактом.
- Дополнительно чинится 500 → 401 для неавторизованных запросов без `Accept` (README это
  зафиксировал как поведение; это дефект, влияющий и на `store`/`destroy`).
- `index` и `today` не меняются — только ревью (прямое требование задания).
